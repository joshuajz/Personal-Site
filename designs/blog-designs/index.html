Building a dependable price-tracking pipeline

The useful architecture was not the cleverest one. It was the one where every stage could fail clearly, recover independently, and explain what happened.

The first version of my Uniqlo price tracker had one job: notice when a product became cheaper. That sounds simple until three separate systems need to agree about what a “product” and a “price” actually are.

Give every stage one responsibility

The scraper collects observations. The API owns product history. The frontend turns that history into a decision someone can make. Keeping those boundaries plain made failures much easier to locate.

type Observation struct {
  ProductID string
  Price     int
  SeenAt    time.Time
}

The result is not a grand distributed system. It is a small pipeline with visible seams—and those seams are exactly what make it dependable.

The architecture of a price drop

How four simple steps turn a storefront change into a useful signal—and how to keep each step honest.

A price drop is an event, but an event is not yet a product feature. Between noticing the change and showing it to someone sits a chain of decisions about identity, time, and trust.

Start with the question

Users do not want a stream of scraped numbers. They want to know whether this is a good time to buy. That question determines what the system must remember.

The architecture became clearer when every layer could be described with one verb: collect, store, compare, explain.

The useful seams in a small system

The boundaries in a codebase should reveal how the product works, not merely where the files live.

There is a moment in most side projects where “just one service” becomes three jobs wearing the same coat. That moment is not a demand for microservices. It is a prompt to name the responsibilities already there.

The first boundary

Collection changes when the source changes. Storage changes when the questions change. Presentation changes when the audience changes. Giving each one a clean seam lets the system evolve at the speed of the thing it follows.

Let failures speak

A useful seam does not hide failure. It makes the failure specific: the storefront changed, the observation was invalid, or the chart could not load.
